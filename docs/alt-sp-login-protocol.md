# Стендовый протокол проверки доменного и автономного входа на ALT СП 10.2.2

**Статус шаблона:** испытание ожидает стенда. Скопируйте файл для каждого прогона. Цель — установить, сможет ли тестовый пользователь открыть **новый интерактивный сеанс** после потери связи со всеми контроллерами, и сопоставить результат с наблюдениями helper до и во время изоляции. Основание — §2.3 и §3.4–3.5 ТЗ.

| FQDN станции, площадка, IP-адреса, домен SSSD | |

| Точный объект и способ изоляции, исходное состояние, команда или действие отмены | |

Используйте сборки **обоих компонентов с поддержкой alt-workstation**. Этот профиль добавлен после v0.36.0. Заранее проверьте независимую консоль и доступ локального администратора. Согласуйте, останется ли DNS доступен, если его обслуживает отдельный сервер. Для испытания автономного входа должны быть перекрыты также пути к региональному RODC. Вход через доступный RODC проверяется отдельным прогоном.

## A. При доступном контроллере

1. Сверьте время станции и DC, запишите смещение и часовой пояс. Подтвердите членство станции в нужном домене, online-состояние SSSD и активный DC командой `sssctl domain-status <домен>`. Сохраните результат и время.
2. С экрана входа откройте новый сеанс тестового пользователя с доменным паролем. В пользовательском терминале выполните `date --iso-8601=seconds`, `id` и `loginctl session-status`. Запишите идентификатор сеанса. Сопоставьте вход с успешным событием аутентификации на DC по UPN, станции и времени. Сохраните ссылку на событие или выдержку. Если журнал DC недоступен, отметьте отдельно: источник онлайн-аутентификации не подтверждён.
3. Из административной консоли задайте параметры один раз. Каталог создаётся отдельно для каждого прогона. Выполните сбор, пока канал доступен:

```sh
site='Region-01'                   # заменить
account='ivanov@corp.example'      # одна и та же запись для A и B
run_dir=$(sudo mktemp -d /var/tmp/sambaadm-login.XXXXXXXX)
snapshot() {
  sudo sambaadm-helper collect --profile alt-workstation \
    --config /etc/sambaadm-helper/config.yaml \
    --site "$site" --account "$account" --out "$run_dir/$1.json"
}
snapshot A-online
```

4. Завершите пользовательский сеанс через «Выйти». По `loginctl list-sessions` подтвердите завершение сеанса A. Оставьте административную консоль открытой. Между фазами сохраните пароль, настройки и содержимое кэша SSSD без изменений.

## B. После отключения канала

1. Запишите время начала изоляции. Примените согласованное ограничение только к тестовой станции. Через независимую консоль сохраните состояние виртуального адаптера либо действующего правила изоляции и его область действия. Учтите альтернативные интерфейсы, IPv6 и UDP. Сохраните результаты проверки ранее доступных доменных служб для каждого DC/KDC. Один тайм-аут ping или отсутствие строки в журнале DC недостаточны для вывода об изоляции.
2. С того же экрана входа введите тот же UPN и пароль. Зафиксируйте время, результат и сообщение об ошибке при отказе. При успехе выполните те же команды, что в фазе A, запишите **новый** ID сеанса и доменный UID. Сохраните относящиеся к попытке строки PAM/SSSD либо ссылку на запись. Разблокировка экрана, SSH по ключу и `su` из root не проверяют этот сценарий.
3. При успехе **и при отказе** выполните `snapshot B-isolated` из оставленной административной консоли до возврата канала. Запишите состояние SSSD после попытки и время конца сбора. Если станция потеряла управляемость или возникло влияние на соседние узлы, сразу перейдите к восстановлению и отметьте прогон как прерванный.

## Восстановление

Отмените ограничение способом из паспорта при любом исходе. Сверьте адаптеры, маршруты и правила с исходным состоянием. Проверьте доступность DNS и доменных служб, online-состояние SSSD и новый вход тестового пользователя. Запишите время снятия ограничения и время фактического восстановления. При неудаче укажите ответственного и оставьте восстановление открытым.

## Сопоставление в sambaadm

1. Выполните `sudo sha256sum "$run_dir/A-online.json" "$run_dir/B-isolated.json"`. Передайте файлы администратору согласованным способом. Пароль, keytab и базы SSSD в материалы прогона не включайте.
2. Под ролью admin откройте «Материалы автономного обследования» (`/surveys`), импортируйте оба файла в формате «Снимок helper». Для каждого сверьте SHA-256, FQDN, площадку и границы сбора. Запишите ID материалов. Фазу определяйте по хешу и времени наблюдения, а не по порядку загрузки.
3. Выберите оба материала и нажмите «Сформировать отчёт». В разделе «§2.3 · Рабочие станции ALT» сопоставьте строки одной станции по источнику и времени. Заполните таблицу. Если инструмент отсутствует или проверка завершилась тайм-аутом, укажите «нет данных» и причину.

| Наблюдение и источник | A — канал доступен | B — канал отключён | Вывод или пробел |
|---|---|---|---|
| Время и результат попытки, UPN/UID, ID сеанса, событие PAM/SSSD и при наличии DC | | | |
| Состояние канала, охваченные DC и доказательство изоляции | | | |
| ID материала, SHA-256, интервал сбора | | | |
| DNS: настроенный резолвер, SERVER диагностического dig, ответы A/AAAA и адреса интерфейсов | | | |
| DC: online/offline и активный сервер из sssctl | | | |
| KDC: адреса локатора kdcinfo и отдельно наблюдавшееся соединение с портом 88 | | | |

Наличие адреса в локаторе не устанавливает, какой KDC выдал билет. Сохранённый GPResult может совпадать в обеих фазах. Для вывода о новом применении политики или новой регистрации DNS требуется событие в соответствующем временном интервале. Журнал за последние сутки в снимке B может содержать событие из фазы A.

## Решение по прогону

- **Автономный вход подтверждён**, если доменная идентичность установлена, сеанс A завершён, изоляция всех DC/KDC подтверждена на момент проверки и в фазе B создан новый сеанс того же пользователя.
- **Получен отказ**, если при подтверждённой изоляции зафиксирована новая попытка входа и система отказала в создании сеанса. Укажите текст отказа и сопоставьте результат с заранее записанной политикой.
- **Недостаточно данных**, если возможен путь к другому DC, не установлен способ аутентификации или нельзя отличить новый сеанс от существующего. Опишите повторную проверку.
- Отдельно оцените полноту двух снимков и восстановление связи. Даже при успешном входе пропуски в DNS, KDC или GPO остаются открытыми.
