# Файловый HA-кластер ZFS на ALT p10 и p11

Samba Admin управляет двумя зарегистрированными helper через подписанные
запросы. Рабочий сценарий использует общий iSCSI LUN, multipath, ZFS и
Pacemaker. Поддерживаются пары p10/p10 и p11/p11. Для развёртывания и
управления снимками используйте веб-раздел «Файловые кластеры» или команду
`sambaadm file-cluster`. [Веб-интерфейс со скриншотами](filecluster-ui/README.md)

У пользователей один путь `\\<виртуальное-имя>\files`. Pacemaker переносит
пул, VIP, отдельный Winbind и Samba как одну группу. Перед импортом на другом
узле Pacemaker подтверждает fencing. ZFS использует `multihost=on` и
`cachefile=none`. Виртуальное имя имеет отдельную учётную запись компьютера
в AD. `state` хранит служебное состояние Samba, а `data` хранит файлы с
POSIX ACL. Именные снимки затрагивают только `data`. Клиент Samba может
получить предыдущую версию файла через `shadow_copy2`.
[Документация Samba по shadow_copy2](https://www.samba.org/samba/docs/4.18/man-html/vfs_shadow_copy2.8.html)

## Подготовка

1. Зарегистрируйте оба helper. Установите пакеты на обоих узлах командой
   `sambaadm file-cluster prepare NODE redfish`. Helper проверяет репозитории,
   скачивает пакеты до установки и сообщает, если требуется перезагрузка.
2. Проверьте, что на обоих узлах загружена одинаковая версия ZFS и у каждого
   собственный постоянный `/etc/hostid`. Для выделенных узлов кластера опишите
   порядок импорта существующих пулов и отключите штатный автоимпорт
   `zfs-import-cache.service` и `zfs-import-scan.service`. Helper остановит
   подготовку, пока автоимпорт включён или его состояние неизвестно.
3. На обоих узлах выполните `file-cluster discover NODE PORTAL1 PORTAL2`,
   затем `file-cluster connect NODE IQN PORTAL1 PORTAL2`. В ответе найдите
   общий WWID. Выполните `file-cluster multipath NODE NAME WWID IQN`.
   Helper сверит WWID, iSCSI-цель, доступность двух порталов и отсутствие
   сигнатур на выбранном LUN.
4. Создайте в DNS запись виртуального имени SMB с адресом VIP. Это имя должно
   быть свободно среди учётных записей компьютеров AD. Контроллер домена
   должен быть доступен обоим узлам по DNS, Kerberos, LDAP/CLDAP и SMB.
   Для Winbind на p11 проверьте также доступность TCP 135 и диапазона
   динамических портов RPC контроллера.
5. Для каждого fencing-устройства сохраните один и тот же идентификатор
   реквизитов на обоих helper командой
   `file-cluster credential NODE REF fence TARGET ADDRESS SYSTEM USER`.
   Затем сохраните реквизиты присоединения только на первом helper:
   `file-cluster credential NODE REF domain-join NODE DC VIRTUAL_FQDN USER`.
   Пароль вводится в приглашении. Реквизиты присоединения удаляются из
   хранилища helper после успешной проверки доменной учётной записи.

## Развёртывание и именные снимки

Сохраните план в JSON с правами 0600. `authKey` содержит 128 случайных байтов
в Base64. `ownerGroupSID` задаёт доменную группу, которой принадлежит корень
ресурса. Порядок в `fences` совпадает с порядком `nodes`. Первый узел
инициализирует LUN после появления обоих узлов в кворуме.

```json
{
  "authKey": "<128 случайных байтов в Base64>",
  "workgroup": "EXAMPLE",
  "controller": "dc1.example.test",
  "ownerGroupSID": "S-1-5-21-111-222-333-513",
  "cluster": {
    "name": "files",
    "realm": "example.test",
    "nodes": [
      {"name": "fs1.example.test", "address": "192.0.2.11", "diskWWID": "360000000000000000e00000000010001"},
      {"name": "fs2.example.test", "address": "192.0.2.12", "diskWWID": "360000000000000000e00000000010001"}
    ],
    "virtualIP": "192.0.2.50",
    "prefix": 24,
    "storage": "iscsi",
    "filesystem": "zfs",
    "portals": ["192.0.2.80:3260", "192.0.2.81:3260"],
    "targetIQN": "iqn.2026-11.test.example:files",
    "fences": [
      {"agent": "redfish", "address": "192.0.2.91:443", "system": "/redfish/v1/Systems/1", "username": "fence", "credentialRef": "<REF1>"},
      {"agent": "redfish", "address": "192.0.2.92:443", "system": "/redfish/v1/Systems/1", "username": "fence", "credentialRef": "<REF2>"}
    ]
  }
}
```

`file-cluster fence-test PLAN.json` по очереди выключает и включает узлы,
проверяет работу fencing и смену boot ID. Выполняйте эту операцию перед
запуском кластера. `file-cluster deploy PLAN.json JOIN_REF` готовит оба helper,
запускает Corosync и Pacemaker, создаёт пул, присоединяет виртуальный сервер
к домену и активирует кластер. Команда возвращает ревизию. Выбранный LUN должен
быть выделен этой паре серверов и свободен от данных.

`file-cluster status NODE NAME REVISION` показывает владельца, кворум и список
именных снимков на активном helper. `file-cluster snapshot NODE NAME REVISION LABEL`
создаёт снимок на активном узле. Отображаемое имя записывается в
`org.sambaadm:label`, а в SMB снимок доступен по адресу `@GMT-…`. После обрыва
сеанса управления `file-cluster job NODE ID` возвращает журнал задания.

## Проверка на стенде

Стенд использует отдельные QEMU ВМ aarch64, отдельный тестовый LUN для каждой
ветки, два iSCSI-портала и программный Redfish, который выключает ВМ через QMP.
Проверка читает и изменяет файл по SMB с обязательной подписью, сверяет POSIX
ACL, блокирует доступ другого доменного пользователя и читает прежнее
содержимое через Previous Versions. Во время проверки одного iSCSI пути
тест закрывает одну реальную сессию и продолжает чтение по второй. Проверка
отключения узла ждёт появления SMB на втором узле с тем же VIP, проверяет запись
успешного fencing. В обратном направлении тест дополнительно записывает
и считывает новый файл после переключения, затем восстанавливает питание
исходного узла.

- ALT p10, ядро `6.1.186-un-def-alt1`, ZFS `2.1.16-1`. Переключение заняло
  53–60 секунд. [Журнал failover](filecluster-tests/ha-p10.log).
- ALT p11, ядро `6.12.117-6.12-alt1`, ZFS `2.4.2-1`. Переключение заняло
  44–45 секунд. [Журнал failover](filecluster-tests/ha-p11.log).

Клиент теста заново подключается по SMB и проверяет синхронизированные данные.
Открытые SMB-дескрипторы, потеря всех путей до СХД и сетевое разделение узлов
не входили в проверку. Сценарии DRBD и LVM/XFS пока имеют предварительный план.
