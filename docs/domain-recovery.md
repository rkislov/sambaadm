# Восстановление первого DC после полной потери домена

Этот сценарий восстанавливает **однодоменный лес** из полной копии
`sambaadm-cold-dc-v1` в **новый каталог и новый RWDC с новым именем**.
Используется штатное восстановление установленной версии Samba: исходная копия
разворачивается во временный каталог, преобразуется в native offline backup,
после чего `samba-tool domain backup restore` создаёт первый DC. База действующего
контроллера не перезаписывается. Службы не останавливаются и не запускаются
автоматически; тестовый запуск происходит только в отдельной сетевой изоляции.

Если другие DC продолжают работать, вместо этого сценария вводите новый DC
в существующий домен. Все прежние DC восстанавливаемого леса должны оставаться
выключенными и изолированными. После восстановления их переустанавливают и
вводят в восстановленный домен заново. Подтверждения в интерфейсе — заявление
оператора: helper не может проверить недоступные площадки и их сетевую изоляцию.

## Подготовка узла и архива

Нужны Linux, root, systemd, Python-модули Samba и `/usr/bin/samba-tool`.
Проверенный стенд — Samba 4.17.12/TDB. Установите ту же версию Samba, которая
создала копию. Новые архивы записывают версию в manifest; несовпадение версии
отклоняется. Для архивов v0.44.0 без записанной версии оператор обязан проверить
её совместимость отдельно. MDB, многодоменные леса, переименование домена и
восстановление одного DC среди работающих реплик этим сценарием не поддерживаются.

В доверенной root-owned конфигурации helper:

```yaml
helper:
  domain_backup_enabled: true
  backup_root: /var/lib/sambaadm-helper/backups
  domain_restore_enabled: true
  domain_restore_root: /var/lib/sambaadm-recovery
  state_dir: /var/lib/sambaadm-helper
```

`domain_restore_root` должен быть отдельным абсолютным каталогом, не совпадать
и не пересекаться с `backup_root`. Не указывайте каталог рабочей базы Samba.
Новые каталоги создаются с `0700`, файлы — `0600`. Для будущей раздачи SYSVOL
допускается только право прохода без чтения/записи у группы/остальных (`0711`).
Приватные базы и файлы конфигурации при этом остаются закрытыми.

Перенесите доверенный каталог полной копии на узел восстановления:

```text
backup_root/domain-backups/<UUID>/
  request.json
  status.json
  restore.json
  domain.tar.gz
```

Владелец — root; каталог `0700`, файлы `0600`. Нужны полный архив со статусом
`backed_up` и квитанция успешной проверки. Архивы очистки топологии не принимаются.
SHA-256 пересчитывается при подготовке и перед запуском. Архив содержит секреты;
не загружайте его в публичные сервисы и не передавайте через форму веб-интерфейса.

Остановите Samba на узле восстановления, оставив helper работающим. Не подключайте
узел к рабочим клиентам до проверки результата. Нужно свободное место для нового
DC, временной исходной копии, native offline backup и отдельной проверочной копии.
Запас должен учитывать несколько полных развёрнутых копий, а не только размер
сжатого архива. Ограничения источника — 10 ГиБ данных и 100 000 путей.

## Локально, когда LDAP и веб-вход недоступны

Локальные команды не требуют LDAP, доменного пароля, ключа управляющего сервера
или действующей веб-сессии. Нужны root и доверенная конфигурация helper.

```sh
sudo sambaadm-helper domain-restore-plan \
  --config /etc/sambaadm-helper/config.yaml \
  --backup-id <UUID-полной-копии> \
  --new-name RECOVER \
  --address 192.0.2.10
```

В ответе JSON проверьте исходный контроллер и домен, время создания/размер копии, SHA-256, новое имя/IP,
`target` и `config`. Сохраните `id` и `revision`. IP в примере замените фактическим
адресом нового DC; настройку сетевого интерфейса helper не выполняет.
Новое NetBIOS-имя — 1–15 букв/цифр/дефисов, оно должно отличаться от исходного DC
и не совпадать с учётной записью в архиве. План действителен один час.

После проверки плана и подтверждения остановки **всех** прежних DC:

```sh
sudo sambaadm-helper domain-restore \
  --config /etc/sambaadm-helper/config.yaml \
  --id <id-из-плана> --revision <revision-из-плана> \
  --confirm-domain-lost --confirm-isolated

sudo sambaadm-helper domain-restore-status \
  --config /etc/sambaadm-helper/config.yaml --id <id-из-плана>
```

Команда запускает systemd-задание с `PrivateNetwork=yes`, приватным `/run`,
лимитом 30 минут и фиксированными командами Samba. Повтор запуска с тем же `id`
возвращает ту же задачу; цель не заменяется. План и статус хранятся в
`domain_restore_root/<id>/`, включая закрытые `worker.log` и `verification.log`.
Незавершённое задание блокирует параллельное восстановление.

## Через веб-интерфейс и API

В `/backups` откройте «Восстановить домен из полной копии», выберите заранее
зарегистрированный helper узла восстановления, введите UUID копии, новое имя
и IPv4. Проверьте план, подтвердите потерю домена и изоляцию. Для запуска и
статуса LDAP не используется. Веб-вход всё ещё требует LDAP: если сессия истекла
или управляющий сервер потерян, используйте локальные команды выше.

Все API требуют `admin`; POST также требует CSRF:

- `POST /api/v1/backups/restore/plan?node=<helper>`:
  `{"backupID":"UUID","newName":"RECOVER","address":"192.0.2.10"}`.
- `POST /api/v1/backups/restore/start?node=<helper>`:
  `{"id":"UUID-задачи","revision":"из-плана","confirmDomainLost":true,"confirmIsolated":true}`.
- `GET /api/v1/backups/restore/status?node=<helper>&id=<UUID-задачи>`.

## Что проверяет восстановление

Штатный механизм Samba создаёт новую DSA и invocation ID, обновляет RID/FSMO,
удаляет прежние DC и их репликационные связи, дважды меняет krbtgt. Пользователи,
их SID/GUID, группы, пароли и данные домена возвращаются к моменту копии;
действия и пароли, изменённые после копии, теряются. Билеты Kerberos прежнего
леса перестают действовать. Некоторые компьютеры могут потребовать восстановления
доверия, если их машинный пароль менялся после копии.

Дополнительно проверяются GUID/SID домена, смена invocation ID, наличие ровно
одной DSA, все семь FSMO, dbcheck и перенос NT/POSIX-прав SYSVOL. Для проверки
точная восстановленная кандидатная база копируется в отдельную временную среду:
там создаётся тестовый пользователь и проверяются вход LDAP, отказ с неправильным
паролем, чтение SYSVOL по SMB, Kerberos TGT/LDAP/CIFS без NTLM-fallback. Все
тестовые процессы завершаются. В постоянной кандидатной базе тестовый пользователь
не создаётся, а исходный архив проверяется повторно и остаётся неизменным.

Только `status: ready` с полной `liveVerification` означает завершённую подготовку.
Это ещё не ввод DC в рабочую сеть.

## Ручной ввод восстановленного DC в эксплуатацию

1. Дождитесь `ready`. Сохраните результат, логи и исходный архив отдельно.
2. Проверьте итоговый `config` из статуса: новое имя/realm, абсолютные пути,
   интерфейсы, DNS и дополнительные секции. Файловые ресурсы за пределами SYSVOL
   этот сценарий не восстанавливает. Настройте hostname/IP и DNS ОС отдельно.
3. Обеспечьте проход к SYSVOL для обычных пользователей через родительские
   каталоги. Для стандартного `target` нужны права прохода у `domain_restore_root`,
   `<id>`, `dc` и `dc/state`, например `0711`. Сами приватные базы `dc/private`
   и файлы с секретами сохраняйте `0700`/`0600`; не делайте всё дерево общедоступным.
   Сохранённые ACL и режимы внутри SYSVOL уже восстановлены.
4. Настройте службу Samba на **итоговый** `config`. По умолчанию службы обычно
   читают `/etc/samba/smb.conf`; helper не меняет этот файл или unit. Все каталоги
   `target` должны оставаться на своих путях: простое перемещение сломает
   абсолютные ссылки конфигурации. Только после этого вручную запустите Samba.
5. Проверьте DNS/SRV и регистрацию нового имени/IP, LDAP, Kerberos, SYSVOL и вход
   обычного пользователя. Штатный offline restore не является настройкой сети ОС.
   Обновите DNS клиентов и конфигурацию LDAP/учётных данных панели при необходимости.
6. Введите дополнительные DC заново. Не запускайте старые базы рядом с
   восстановленным лесом. Проведите отдельную приёмку перед подключением клиентов.

При `failed`, `unknown` или `interrupted` не запускайте частичную цель. Сначала
прочитайте приватные логи и проверьте отсутствие работающего worker. Частичные
каталоги сохраняются для анализа; автоматического удаления, отката в рабочую
базу и повторной перезаписи нет. После выяснения причины подготовьте новую задачу
с новым UUID. Поддерживаемый путь восстановления всегда создаёт новый каталог.
